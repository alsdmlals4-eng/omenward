# Codex Plan Mode 제안서 작업 흐름

이 프로젝트의 코드·아키텍처·데이터 구조 변경은 Codex가 바로 구현하지 않는다. 먼저 **Plan Mode에서 읽기 전용 검토를 수행하고 제안서를 제출한 뒤**, 사용자의 명시적 승인을 받아 구현한다.

## 기본 흐름

```text
기획 확정 및 GitHub 반영
→ Issue/Goal을 `제안서 검토 대기` 상태로 준비
→ Codex Plan Mode 읽기 전용 조사
→ 제안서 제출
→ 사용자 검토·수정·승인
→ 구현용 Issue/Goal 확정
→ 기능 브랜치 구현·검증
→ Pull Request
```

## Plan Mode 금지 사항

사용자 승인 전에는 다음을 하지 않는다.

- 게임 코드, Scene, Resource, 데이터 파일 생성·수정
- `project.godot` 생성 또는 변경
- 애드온·에셋·외부 의존성 설치
- 구현 브랜치 또는 Pull Request 생성
- 미확정 결정을 사실상 코드로 고정
- 제안서 범위를 넘어선 리팩터링이나 시스템 추가

Plan Mode에서는 저장소와 참고 문서를 읽고, 구현 계획과 위험을 설명하는 데 집중한다.

## 제안서 품질 기준

- 구현 파일을 읽지 않고 추측한 경로나 API를 확정안으로 쓰지 않는다.
- 한 가지 권장안과 필요한 대안만 비교한다.
- 장문 벤치마킹 전문 대신 프로젝트에 적용할 결론을 적는다.
- `Base`와 `urban-legend`의 코드를 그대로 복사하지 않고 채택·제외 이유를 남긴다.
- 완료 기준은 기능명이 아니라 실행 또는 화면에서 확인 가능한 결과로 작성한다.
- 정확한 Godot 버전, 명령, 경로가 미확정이면 `확인 필요`로 표시한다.

## 승인 표현

다음과 같이 사용자가 구현 진행 의사를 명확히 밝혀야 승인으로 본다.

- `제안서 승인`
- `이 계획으로 구현 진행`
- 승인 범위가 명시된 동등한 표현

단순한 의견, 질문, 부분 동의는 구현 승인으로 간주하지 않는다. 제안서가 수정되면 변경된 범위를 다시 검토받는다.
