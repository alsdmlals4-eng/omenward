# 특수병 병영 T1 무작위 선정·공개 시점 설계

```yaml
decision_id: OMW-DEC-20260806-PLANNING-SPECIAL-T1-RANDOM-SELECTION-AND-PREVIEW-TIMING-V1
parent_decision_id: OMW-DEC-20260805-PLANNING-FIRST-10-15-MINUTES-FLOW-V1
status: USER_APPROVED_DESIGN / NOT_IMPLEMENTED
approved_option: CONSTRUCTION_COMMIT_ONE_ROLL_IMMEDIATE_REVEAL
```

## 1. 목표

특수병 병영 T1의 무작위성을 다음처럼 플레이 가능한 불확실성으로 만든다.

```text
투자 결정
→ 건설 거래 확정
→ 병영별 특수병 1종 추첨
→ 즉시 결과 공개
→ 생산 전 전략 조정
→ 선정 병종 반복 자동생산
→ T2에서 원하는 계열 직접 전문화
```

무작위성은 투자 결과를 바꾸지만 저장·취소 반복으로 무료 선택으로 변해서는 안 된다.

## 2. 검토한 접근

### 접근 A — 건설 전 결과 공개

기각. 결과 확인 후 건설하지 않는 방식으로 무작위성의 비용을 우회할 수 있다.

### 접근 B — 건설 완료 직후 한 번 확정하고 즉시 공개

채택.

- 투자 확정 뒤 결과가 정해진다.
- 첫 생산 전에 결과를 알 수 있다.
- 병영별 생산 정체성이 생긴다.
- T2의 선택 전문화와 명확한 대비를 만든다.

### 접근 C — 첫 생산 완료 시 공개

기각. 긴 생산시간 동안 대응 계획을 세울 정보가 부족하다.

### 접근 D — 매 생산마다 재추첨

기각. 병영 역할과 전선 계획을 안정적으로 예측할 수 없고 T2 전문화 가치가 약해진다.

## 3. 승인 설계

```text
SPECIAL_T1_SELECTION_TRIGGER
= SUCCESSFUL_CONSTRUCTION_COMMIT

SPECIAL_T1_SELECTION_POOL
= MAGE / PRIEST / ASSASSIN / FLYING_UNIT / GIANT

SPECIAL_T1_SELECTION_COUNT
= ONE_PER_BUILDING
```

각 특수병 병영은 건설 거래가 원자적으로 성공한 뒤 한 번 추첨한다. 여러 병영은 독립적으로 추첨하며 T1 동안 선정 결과를 유지한다.

## 4. UI 흐름

```text
건설 위치·비용 확인
→ 플레이어 건설 확정
→ 골드 차감·노드 점유·건물 생성 커밋
→ 결과 공개 패널
→ 병종 이름·아이콘·역할 표시
→ 첫 생산 카운트다운 시작
→ 일반 HUD 상태로 전환
```

결과 공개 패널 필수 정보:

- `선정 병종: [이름]`
- 역할 한 문장.
- `첫 생산까지: [남은 시간]`
- `T1 동안 이 병종을 생산합니다.`
- `T1은 룰렛 토큰을 추가하지 않습니다.`
- `T2에서는 원하는 특수병 계열을 선택할 수 있습니다.`

정확 문장·연출·아이콘 배치는 UX 작업에서 조정할 수 있으나 의미는 유지한다.

## 5. 상태 모델

```text
UNBUILT
→ CONSTRUCTION_PENDING
→ CONSTRUCTION_COMMITTED
→ T1_IDENTITY_REVEALED
→ T1_PRODUCING_SELECTED_UNIT
→ T2_SPECIALIZATION_PENDING
→ T2_SELECTED_UNIT_PRODUCING_AND_TOKEN_SOURCE
```

필수 저장 상태:

- 건물 인스턴스 식별자.
- 현재 Tier.
- T1 선정 병종.
- 선정 결과 공개 완료 여부.
- 현재 생산 타이머의 남은 시간.
- T2 전문화 선택과 TokenSource 상태.

저장 복구는 기존 T1 선정 병종과 남은 타이머를 복원하며 재추첨하지 않는다.

## 6. 원자적 건설 거래

다음 상태를 하나의 커밋 경계로 취급한다.

```text
골드 차감
+ 노드 점유
+ 건물 인스턴스 생성
+ T1 선정 결과 저장
```

하나라도 실패하면 건물·노드·골드·선정 결과를 모두 이전 상태로 복구한다. 실패한 건설 결과를 UI에 공개하거나 저장에 남기지 않는다.

정확한 RNG stream 소비와 롤백 방식은 제품 구현 계획에서 결정하되 같은 Run 상태의 재현 가능성을 검증해야 한다.

## 7. 재추첨 방지

```text
SAVE_RELOAD_REROLL = FORBIDDEN
FREE_CANCEL_AFTER_REVEAL = FORBIDDEN
FREE_DEMOLISH_REBUILD_REROLL = FORBIDDEN
```

허용되는 철거·재건설은 본편 경제 규칙을 사용한다. 환급률·건설시간·병종 가치 때문에 반복 재건설이 자동 최적 전략이 되면 경제 수치를 재조정한다.

## 8. T2 연결

T2는 T1의 무작위 정체성을 강화하는 것이 아니라 플레이어가 원하는 특수병 계열을 직접 선택해 불확실성을 통제하는 단계다.

```text
T1 = RANDOM_IDENTITY / NO_TOKEN_SOURCE
T2 = PLAYER_SELECTED_IDENTITY / SELECTED_TOKEN_SOURCE
```

T2 업그레이드 시 진행 중인 T1 생산 처리 방식은 별도 제품 거래 계약으로 남긴다.

## 9. 전투 설계 가드레일

- 다섯 병종 모두 해당 Run에서 유효한 활용처가 있어야 한다.
- 다음 전투가 특정 T1 특수병을 필수로 요구해서는 안 된다.
- 무작위 결과는 전선 배치·상점·다음 건설 우선순위를 바꾸는 변수로 사용한다.
- 결과에 따른 기능가치 차이는 생산시간·비용·가중치와 함께 시뮬레이션한다.

## 10. 검증 요구사항

### 계약 테스트

- 건설 성공 후 한 번 추첨하는지.
- 병영별 독립 결과인지.
- T1 동안 같은 병종만 생산하는지.
- 결과 공개 후 타이머가 시작되는지.
- T1 TokenSource가 없는지.
- 저장·복구가 재추첨하지 않는지.
- T2가 플레이어 선택으로 T1 결과를 대체하는지.

### 시뮬레이션

- 병종별 기대 전투가치와 분산.
- 동일/차등 가중치 비교.
- 생산시간·비용·환급률과 재건설 기대값.
- 특정 결과가 무가치하거나 압도적이지 않은지.

### 사람 QA

- 결과가 건설 뒤 확정된다는 사실을 이해하는지.
- 공개가 즉시 병력 지급이 아니라 생산 대상 공개임을 이해하는지.
- T2에서 원하는 계열을 선택할 수 있음을 이해하는지.
- 결과가 달라도 플레이 계획을 세울 수 있는지.

## 11. 범위 밖

- 정확 추첨 가중치.
- 정확 건설·생산 시간과 비용.
- 환급률.
- RNG 알고리즘·시드 스키마.
- 저장 마이그레이션.
- UI·Scene·Resource·제품 코드 구현.

## 12. 자체 검토

- 선정 시점과 공개 시점이 분리되지 않고 명시되어 있다.
- 병영별 1회 추첨과 매 생산 재추첨 금지를 명시했다.
- 저장·취소를 통한 무료 재추첨을 차단했다.
- T1 TokenSource 없음과 T2 선택 전문화를 유지했다.
- 수치와 제품 구현은 별도 Gate로 남겼다.
