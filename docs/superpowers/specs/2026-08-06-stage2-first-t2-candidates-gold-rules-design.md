# Stage 2 최초 T2 후보·골드 규칙 설계

```yaml
decision_id: OMW-DEC-20260806-PLANNING-STAGE2-FIRST-T2-CANDIDATES-AND-GOLD-RULES-V1
parent_decision_id: OMW-DEC-20260805-PLANNING-FIRST-10-15-MINUTES-FLOW-V1
status: USER_APPROVED_DESIGN / NOT_IMPLEMENTED
approved_option: FIXED_SHIELD_VS_ARCHER_SAME_BARRACKS
```

## 1. 목표

Stage 2의 첫 건물 선택으로 다음 인과를 짧고 명확하게 학습시킨다.

```text
일반병 병영 전문화
→ 자동생산 병종 변화
→ TokenSource 변화
→ 룰렛 후보 구성 변화
→ 전선 판단 변화
```

첫 선택은 실전 선택이어야 하며, 한 후보가 정답으로 강제되거나 튜토리얼 전용 경제 규칙에 의존해서는 안 된다.

## 2. 검토한 접근

### 접근 A — 같은 병영의 방패병·궁병 고정 후보

**채택.**

- 두 경로 모두 자동생산과 TokenSource를 바꾼다.
- 방패병의 생존·지연과 궁병의 지속 원거리 화력을 비교한다.
- 같은 건물·같은 비용 축으로 비교해 설명 부담을 최소화한다.

### 접근 B — 일반병 병영과 방어탑 교차 후보

**기각.**

- 방어탑 경로는 룰렛 TokenSource를 바꾸지 않아 학습 결과가 경로별로 달라진다.
- 이동 병력과 고정 방어의 차이까지 동시에 설명해야 한다.

### 접근 C — 전투 결과·예고 기반 동적 후보

**보류.**

- 재플레이 다양성은 높지만 첫 플레이 QA 경우의 수가 증가한다.
- 고정 후보의 원인 복기와 밸런스가 검증된 뒤 후속 모드에서 검토한다.

## 3. 승인 설계

```text
FIRST_STAGE2_T2_CANDIDATES
= GENERAL_BARRACKS_T2_SHIELD
/ GENERAL_BARRACKS_T2_ARCHER
```

Stage 1에서 설치한 일반병 병영을 하나 선택해 두 후보 중 하나로 T2 전문화한다.

### 방패병

- 전열 생존과 적 진입 지연.
- 후열·방어 건물이 기여할 시간을 확보.
- 자동생산과 TokenSource를 방패병으로 변경.

### 궁병

- 지속 원거리 화력과 후열 기여.
- 기본 비행 적 우선 대응을 장기 강점으로 보유.
- 자동생산과 TokenSource를 궁병으로 변경.

## 4. UX 흐름

```text
Stage 2 실제 골드 지급
→ 방패병·궁병 비교 카드
→ 자동생산 전후 비교
→ TokenSource 전후 비교
→ 역할·다음 압력 대응 비교
→ 비용·잔여 골드 비교
→ 플레이어 확인
→ 병영 T2 업그레이드
→ 첫 Stage 2 룰렛
→ 업그레이드 전후 결과 복기
```

비교 카드에는 다음 문구를 반드시 포함한다.

- 방패병: `전선을 오래 유지합니다.`
- 궁병: `후열에서 지속 화력을 제공합니다.`
- 공통: `선택하지 않은 분기는 이후 다른 일반병 병영에서 선택할 수 있습니다.`

정확 UI 문장·아이콘·배치는 후속 UX 작업에서 조정할 수 있으나 의미는 유지한다.

## 5. 경제 규칙

```text
FIRST_STAGE2_PAIR_COST_CLASS = SAME
STAGE_2_REAL_GOLD_GRANT = ONE_CANDIDATE_COST
STAGE_2_REQUIRED_COST_RESERVE = ONE_FIRST_T2_UPGRADE
```

- 지급액은 실제 골드다.
- 두 후보는 같은 비용 등급이다.
- 선택 전 후보 외 소비는 차단한다.
- 지급액에 의도적인 잉여를 포함하지 않는다.
- 기존 지갑 잔액은 보존하며 선택 뒤 정상 골드로 사용한다.
- 튜토리얼 전용 할인·환급·가짜 통화는 사용하지 않는다.

## 6. 전투 검증 설계

다음 전투는 지속되는 혼합 지상 압력으로 구성한다.

- 방패병 경로: 전선을 오래 유지해 후열과 건물의 총 기여시간을 늘린다.
- 궁병 경로: 지속 화력으로 적 수를 빠르게 줄여 압력을 낮춘다.
- 비행병·특정 방어탑·특정 T2가 없으면 실패하는 하드키는 두지 않는다.
- 정확 적 구성과 수치는 시뮬레이션에서 정한다.

## 7. 실패 처리

업그레이드는 다음 상태를 하나의 원자적 거래로 취급한다.

```text
골드 차감
+ 병영 Tier 변경
+ 자동생산 병종 변경
+ TokenSource 변경
```

하나라도 실패하면 전부 이전 상태로 복구한다. 선택 확인 뒤 단순 변심에 의한 무료 분기 변경은 허용하지 않는다.

## 8. 검증 요구사항

### 계약 테스트

- 두 후보가 정확히 방패병·궁병인지 확인.
- 같은 병영의 두 분기인지 확인.
- 실제 골드·예약·잔여 골드 규칙 확인.
- 미선택 분기의 전역 잠금 금지 확인.
- 혼합 소프트 카운터와 제품 경계 확인.

### 시뮬레이션

- 동일 비용에서 두 경로의 생존시간·처치시간·룰렛 안정성 비교.
- TokenSource 변화가 첫 Stage 2 룰렛에서 관찰 가능한지 확인.
- 어느 한 경로가 모든 지표를 독점하면 후보·수치 재검토.

### 사람 QA

- 플레이어가 두 선택의 차이를 설명할 수 있는지.
- 한 후보를 명백한 정답으로 인식하는지.
- 미선택 분기가 영구 소실되지 않음을 이해하는지.
- 골드 지급·예약·잔여 골드 규칙을 자연스럽게 이해하는지.

## 9. 범위 밖

- 정확 T2 비용.
- 자동생산 시간.
- TokenSource 수와 가중치.
- Stage 2 정확 적 조합·수량·시간.
- 방패병·궁병의 제품 데이터 변경.
- UI·Scene·Resource·저장 데이터 구현.
