---

## 1. 목적

화면 보드는 다음 질문에 답해야 한다.

> 건물과 TokenSource로 세 물리 릴을 설계하고, 남은 무작위성을 감수해 얻은 병력을 한 전선에 비가역적으로 배치한 뒤 결과를 복기하는 게임이 실제 화면에서는 어떻게 읽히는가?

필수 증명:

1. 일반 판타지 RPG·영웅 파티·아이템 수집 게임이 아니다.
2. 하나의 전장 안에서 세 라인이 동시에 존재한다.
3. 건물은 TokenSource와 전선 기능을 가진다.
4. 룰렛은 독립 원판 3개나 임의 9칸 추첨이 아니라 세 물리 릴과 3×3 노출 보드다.
5. 결과 병력은 보관·판매·한 라인 배치 중 하나로 처리한다.
6. 배치 뒤 라인 변경·회수·판매가 불가능하다.
7. 전투 결과는 건물→토큰→릴→결과→배치→전투의 인과로 복기한다.

## 3. 통합 보드 구도

향후 통합 보드는 `2560×1440`, 16:9 한 장을 기본 권장안으로 사용한다.

```text
상단: 011 | 012 | 013
중단: 014 | 015 | 016
하단:     017 | 018
```

- `3-3-2` 중앙 정렬.
- 각 패널은 독립적인 16:9 인게임 스크린샷처럼 보인다.
- 보드 제목 영역은 전체 높이의 5% 이하.
- 패널 내부 실제 화면·환경·유닛·UI 비중은 80% 이상.
- 화면 번호·이름은 작게 표시하되 증거 상태·기술 상태는 이미지 안에 넣지 않는다.
- 설명문·흐름도·기술 footer를 넣지 않는다.

통합 보드는 독립 화면 이미지가 검수된 뒤 마지막에 조립한다. 처음부터 한 장에 8개 화면을 동시에 생성하지 않는다.

## 4. 공통 시각 언어

### 4.1 아트

- 전술 픽셀 아트.
- 유닛은 2.5~3등신 미니어처 실루엣.
- 고해상도 픽셀 조명은 제한적으로 사용한다.
- 배경보다 전선·건물·전조·상호작용 대상의 value 대비를 높인다.
- 과도한 bloom·입자·장식으로 노드·전조·병력을 가리지 않는다.

### 4.2 아군 언어

```text
형태: 수직선·아치·방패·종·천 배너
색: 네이비·아이보리·쿨 그레이
강조: 절제된 따뜻한 금속색
```

### 4.3 적·베일 언어

```text
형태: 비대칭 균열·갑각·가시·공허 구멍
색: 흑자주·암적색·갑각 회색
발광: 제한된 내부 발광
```

### 4.4 UI

- 짙은 전술 패널.
- 얇은 금속 프레임.
- 금색은 선택·확정·현재 조작의 제한적 강조에 사용한다.
- 위험은 적색 하나에만 의존하지 않고 형태·아이콘·텍스트·움직임을 병행한다.
- UI 우선순위는 `즉시 위험 → 현재 선택 → 분석 정보`다.

### 4.5 해상도

- 제품 기준: internal `960×540`, override `1920×1080`, integer scaling.
- 화면 명세는 `1920×1080`을 기준으로 작성한다.
- `1280×720`에서 핵심 텍스트·아이콘·전조가 유지되는지 후속 검수한다.
- 최종 글꼴·픽셀 크기는 실제 Godot 화면 검증 전 확정하지 않는다.

## 5. 전장 표현 불변 조건

모든 준비·전투·보스 화면은 다음 토폴로지를 공유한다.

```text
아군 본진
→ 아군 중간 거점
→ 중앙 접전지
→ 적 중간 거점
→ 적 본진
```

- 상·중·하 세 라인이 한 전장 안에서 동시에 읽힌다.
- 양 진영 본진 건설 노드: 각각 6개.
- 중간 거점: `3라인 × 2진영 = 6곳`, 각 3개.
- 중앙 접전지: 3곳, 건설 노드 0개.
- 전체 건설 노드: 30개.
- 노드는 하나의 `CONSTRUCTION_NODE` 유형만 사용한다.
- 접전지에 건설 노드를 그리지 않는다.
- 노드 하나와 릴 하나가 대응하는 것처럼 연결하지 않는다.
- 미니맵을 추가하지 않는다. 전장 자체가 주 정보면이다.

## 6. 세 물리 릴 표현 불변 조건

- 왼쪽·중앙·오른쪽 세 원형 `TokenInstance` 배열이 존재한다.
- 화면 중앙에는 각 릴에서 노출된 연속 3칸, 총 3×3 보드가 보인다.
- 위·아래 숨은 토큰이 이어진다는 원형 연속성을 시각적으로 암시한다.
- 각 토큰은 심벌뿐 아니라 TokenSource 출처를 추적할 수 있다.
- 세로 이동은 한 릴의 cursor를 이동한다.
- 가로 이동은 선택 행의 세 TokenInstance 전체를 순환 교환한다.
- 이동은 실행 즉시 소비되며 되돌리기·전체 초기화가 없다.
- preview와 실행된 live 상태는 명확히 구분한다.
- 정지 뒤 `SpinSnapshot`과 최종 확정을 구분한다.

정확한 회전 비용·이동 아이템 수량·경제값은 미확정이므로 이미지·와이어프레임에서는 `[값 미정]`, 기호 또는 비수치 placeholder를 사용한다.

## 7. 벨루 공통 규칙

- 정본명은 `벨루 / Belu`다.
- 과거 별칭 `율비`를 신규 UI·파일·대사에 사용하지 않는다.
- 작은 비모달 안내·경고·결과 반응만 담당한다.
- 자동 건설·자동 릴 이동·자동 배치·정답 강요를 하지 않는다.
- 실제 사용자 제공 외형 방향을 참고하되 최종 픽셀 크기·프레임·장신구를 발명하지 않는다.
- 같은 화면에서 핵심 조작보다 더 큰 시각 비중을 차지하지 않는다.

## 8. 이미지 안 텍스트 규칙

허용:

- `OMENWARD` 제품명.
- 화면 번호·화면 이름.
- 실제 HUD의 Stage·Act·라인·현재/다음 위협.
- 실제 버튼과 짧은 경고.
- 벨루의 한두 문장 안내.

금지:

- `CURRENT / INFERRED / PROPOSED / PLACEHOLDER` 범례.
- PASS/FAIL, GitHub, Sheet, PR, commit, node/scene 구조.
- 구현 상태·테스트 상태·기술 위험 보고서.
- 화면 전환 다이어그램.
- 패널별 장문 설명.
- 임의로 만든 정확 수치·재화명·병종명·건물 성능.

- 영웅 파티 초상화 행렬.
- 장비 슬롯·무기/방어구 인벤토리 격자.
- 레벨·경험치 바 중심 화면.
- 아이템 희귀도 카드와 랜덤 뽑기 연출.
- 유물·룬·보석 수집판.
- 캐릭터 능력 핫바 중심 전투.

- 전장을 대체하는 추상 미니맵.
- 현실 화폐·상점 결제를 연상시키는 Retry 표현.

9. 벨루가 플레이어 결정을 대신하지 않는다.
10. 기존 폐기 이미지의 구도·잘못된 구조를 재사용하지 않는다.
