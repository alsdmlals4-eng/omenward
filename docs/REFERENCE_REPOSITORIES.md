# 참고 저장소 적용 기준

이 문서는 `Base`와 `urban-legend`에서 Roulettebound에 활용할 구조와 작업 방식을 기록한다. 참고 저장소의 코드를 통째로 복사하거나 변경사항을 자동 병합하지 않는다.

## 기준 버전

- Base: `alsdmlals4-eng/Base` 기준 커밋 `f8cf0a134f4ade34d5c1c74fa93fd0b7c9dc4019`
- urban-legend: `alsdmlals4-eng/urban-legend` 검토 커밋 `b36c82c3a44cc4104295766e1f32c93274001ad4`
- 검토일: `2026-07-14`

참고 저장소가 변경되어도 이 문서의 적용 결론은 자동 변경되지 않는다. 새 구조를 가져올 때는 차이를 확인하고 별도 Issue/커밋으로 갱신한다.

## Base에서 채택

### 1. Spec-first 협업

`사용자 의견 → 질문과 구체화 → 확정 사양 → Issue/Goal → 구현 → 검증 → Compound 회고` 순서를 기본으로 사용한다.

### 2. 역할 분리

- ChatGPT: 기획, 문서, Issue, Goal, 검수 기준
- Codex: 실제 diff, 테스트, 커밋, PR
- 사용자: 방향과 중요한 결정 승인

### 3. 최소 변경과 관찰 가능한 완료 기준

기능 이름만 완료 조건으로 쓰지 않는다. 플레이어 또는 개발자가 실제로 확인할 수 있는 조건과 실행 명령을 기록한다.

### 4. 검증 우선 보고

실행하지 않은 테스트를 통과했다고 쓰지 않는다. 변경 파일, 이유, 검증 결과, 미검증, 위험을 분리한다.

### 5. 문서 라우팅과 로컬 기준

매 작업마다 모든 문서를 읽지 않고 `DOCUMENTATION_MAP.md`를 통해 필요한 문서만 선택한다. 공용 원격 문서보다 이 저장소에 확정된 로컬 규칙을 우선한다.

## Base에서 그대로 가져오지 않음

- 다른 프로젝트의 엔진·세계관·저장 구조
- 프로젝트에 존재하지 않는 도구나 플러그인 강제
- 작은 문서 작업에도 과도한 산출물과 gate를 요구하는 운영
- Base 원격 변경의 자동 병합

## urban-legend에서 채택

### 1. Godot 기본 폴더 분리

- Scene: `scenes/`
- 코드: `scripts/`
- 정적 데이터: `data/`
- 공유 Resource: `resources/`
- 검증: `tests/`

Roulettebound는 전투·건물·룰렛·웨이브의 도메인별 하위 폴더를 필요할 때 추가한다.

### 2. 상태 소유자 단일화

여러 Scene이 공유하는 세션 상태와 서비스만 AutoLoad에 둔다. Scene의 임시 표시 상태와 전투 객체 상태는 해당 Scene/노드가 소유한다. 같은 값을 AutoLoad와 Scene이 동시에 원본으로 관리하지 않는다.

### 3. 데이터 기반 설계

urban-legend가 에피소드 데이터를 코드와 분리한 것처럼, Roulettebound도 다음 항목을 코드에서 분리한다.

- 병종 능력치와 상성
- 건물 티어·생산량·생산시간
- 룰렛 토큰과 보상
- 적 웨이브 구성
- 포탑 공격력·사거리 업그레이드

Godot 편집기에서 자주 조정할 밸런스는 `Resource`/`.tres`를 우선 검토하고, 외부 도구 편집·대량 테이블이 필요한 데이터만 JSON/CSV를 검토한다.

### 4. Godot 네이티브 UI

- `Control`, `Container`, `Theme`, 재사용 Scene 사용
- UI 컴포넌트는 표시 데이터를 입력받고 사용자 의도를 Signal로 반환
- UI 컴포넌트가 전역 게임 상태를 직접 수정하지 않음
- 슬롯, 대기 유닛 카드, 건설 노드 카드, 웨이브 전조 카드처럼 반복되는 단위만 컴포넌트화
- 별도 CSS/가상 DOM/범용 데이터 바인딩 프레임워크를 만들지 않음

### 5. 검증 순서

변경 성격에 따라 다음 순서를 사용한다.

1. 데이터 파싱 및 정적 검사
2. `git diff --check`
3. Godot headless 파싱/실행
4. 변경 Scene 단독 확인
5. 영향받는 실제 플레이 경로 확인

### 6. 보호 경로와 고위험 변경

프로젝트가 시작되면 다음 후보를 보호 경로로 관리한다.

- `project.godot`
- 핵심 AutoLoad 상태 스크립트
- 룰렛 확률·상성·경제의 책임 원본 데이터
- 저장 스키마가 도입된 이후의 저장 코드

보호 경로는 외부 산출물을 자동 적용하지 않고 Codex가 직접 diff와 실행 결과를 확인한다.

## urban-legend에서 그대로 가져오지 않음

- 비주얼노벨·조사·에피소드 전용 Scene과 데이터 스키마
- `battle_scene` 명칭과 괴이 회수 규칙
- urban-legend의 F2 UI 편집기, 콘텐츠 override 저장 구조
- 기존 AutoLoad 이름과 게임 상태 필드
- 도시괴담 세계관, 대사, 자산
- 프로젝트 규모에 비해 아직 필요하지 않은 대형 문서 체계

## Roulettebound 전용 확장

urban-legend에 없는 다음 구조는 새로 설계한다.

- 다수 유닛의 3라인 이동·타기팅·교전
- 건물 노드와 시설 파괴·폐허·재건설
- 건물 개수에서 생성되는 릴별 토큰 풀
- 접전지 점령과 초당 금화
- 30초 전조 기반 적 웨이브
- 전방 포탑과 중앙 접전지 거리 검증
- 성능 예산과 최대 동시 유닛 수 검증

## 작업별 참고 절차

1. 현재 Issue/Goal의 문제를 먼저 정의한다.
2. Base에서는 작업 절차와 검증 원칙만 찾는다.
3. urban-legend에서는 같은 Godot 문제를 해결한 구조가 있는지 필요한 파일만 확인한다.
4. Roulettebound의 플레이 경험·성능·데이터 요구와 맞지 않는 부분을 제외한다.
5. 채택할 구조, 제외할 구조, 변경 파일과 검증을 Issue/Goal에 기록한다.
6. 구현 후 실제 이득이 확인된 원칙만 프로젝트 규칙 또는 Base 승격 후보로 남긴다.
