## 1. 플레이어 경험 약속

플레이어는 위협을 읽고 릴/빌드를 설계한 뒤 배치하고, 전투 결과를 다음 설계 판단으로 연결해야 한다.

```text
위협 예고 확인
→ 현재 릴·자원·배치 가능성 판단
→ 선택 비용과 기대 효과 비교
→ 배치/실행
→ 전투 결과와 원인 확인
→ 다음 릴 설계·배치 수정
```

핵심 경험은 **다가오는 위협을 예측하는 긴장**, **제한된 자원으로 방어 계획을 짜는 고민**, **결과를 이해해 다음 설계가 좋아지는 학습**이다.

## 2. 범위와 보호 대상

포함:

- 위협 예고·릴 설계·배치·전투 결과·복기
- 3라인 정보 우선순위와 시선 이동
- 비용·제약·예상 효과 비교
- 위험·중단·실패 원인·다음 행동
- 키보드·마우스·게임패드 포커스

제외:

- 전투·위협·릴·배치 규칙과 수치 변경
- 제품 Scene·script·data·asset 수정
- HTML 기획 대시보드

UI는 권위 상태를 표시하고 선택·배치·확인 의도만 Signal/Command로 반환한다.

## 3. 화면 중심 질문

| 단계 | 중심 질문 | 첫 시선 | 핵심 행동 | 결과·복귀 |
|---|---|---|---|---|
| 위협 예고 | 무엇이 언제 위험한가 | 가장 임박한 위협 | 대응 우선순위 선택 | 릴/배치 설계로 이동 |
| 릴 설계 | 어떤 조합이 현재 위협에 맞는가 | 제약과 시너지 차이 | 릴 구성 | 유효성·비용 확인 |
| 배치 | 어디에 무엇을 놓을 것인가 | 유효 위치와 영향 범위 | 배치/이동/취소 | 실행 전 전체 계획 확인 |
| 전투 | 지금 어떤 원인으로 전선이 변하는가 | 임박 위험·핵심 충돌 | 제한된 개입 | 인과 로그 축적 |
| 결과/복기 | 무엇이 성공·실패를 만들었는가 | 위협→대응→결과 순서 | 다음 설계 선택 | 이전 맥락으로 복귀 |

## 5. 3라인 정보 우선순위

- 각 라인은 같은 시각 문법을 사용하되 현재 가장 위험한 라인을 명확히 강조한다.
- 강조는 색만 사용하지 않고 위험 아이콘·텍스트·시간·형태를 결합한다.
- 모든 라인의 상세 정보를 상시 노출하지 않고 L0 위험, L1 선택 비교, L2 결과 복기로 분리한다.
- 화면 중앙 연출이 위협·비용·입력 가능 상태를 가리지 않는다.
- 게임패드 이동 순서는 시각적 라인 순서와 일치한다.

## 6. Godot 구현 경계

```text
위협·릴·배치 권위 상태
→ 화면용 View Data
→ Control/Container/Theme 표시
→ 선택·배치·실행 요청 Signal
→ 도메인 처리
→ 전투 Event와 결과 상태
→ 인과 로그·복기 UI
```

금지:

- UI에서 위협 우선순위·피해·시너지·배치 가능성을 재계산
- 연출 완료를 전투 처리 시점으로 사용
- UI 정렬이 도메인 순서를 변경
- 기존 V2 코어·릴·배치 규칙을 UX 명목으로 변경

## 7. 접근성·폴백

- 위험과 성공/실패는 색·소리·모션 하나에 의존하지 않는다.
- 전투 속도·연출 감소에서도 원인과 결과 순서가 남는다.
- 게임패드·키보드·포인터 중 선언된 입력 경로로 준비→배치→실행→복기를 완주한다.
- modal 종료 후 이전 릴/배치 항목으로 포커스가 돌아간다.
- 긴 한국어와 최대 수치에서 라인·카드·툴팁이 겹치지 않는다.
