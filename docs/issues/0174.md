## Phase 1 — GUT RED first

Using Godot AI/HiGodot, create the minimum GUT test script(s) under a dedicated project test path such as `tests/gut/` before changing battle runtime code. The tests must cover all of these package requirements:

1. Priest deterministically selects the lowest-health same-lane ally; effective heal and overheal are distinct.
2. Priest encouragement/buff occurs only when there is no valid heal target; uptime is observable.
3. Mage cluster target selection is deterministic and primary vs collateral damage is separated.
4. Physical damage exercises armor; magic damage exercises `base_stats.magic_resistance`.
5. Flier reaches same-lane backline through its own deterministic path and emits first-contact timing.
6. Archer anti-air priority can select Flier when applicable.
7. Giant slam is bounded and deterministic, excludes air targets, and preserves existing siege objective output.
8. `BLOCKED_RUNTIME_OUTPUT` is never serialized as numeric zero.
9. Event ordering is identical for identical deterministic input.
10. Zero-test discovery is a hard failure, never PASS.

Run the new tests and preserve the failing output as RED evidence. GUT CLI entry point verified in the repository:

```text
Godot_v4.7.1-stable_win64.exe --headless --path . -s addons/gut/gut_cmdln.gd -gtest=res://<new-test-path>.gd -gexit
```

Use the actual local Godot executable path if it differs. Do not proceed to implementation unless tests are discovered (>0) and fail for the intended missing runtime behavior.

## Phase 2 — HiGodot persistent authoring

Only after RED, use Godot AI/HiGodot for persistent Godot-source mutations. Follow the approved minimal architecture; do not create a generic ability framework.

Preferred existing surfaces:
- `scripts/battle/unit_instance.gd`

- existing `role`, `base_stats.magic_resistance`, `target_priority_tags`, `attack_profile_id`, `structure_damage_tags`
- existing `_record_event()` / `drain_events()` event surface

Only add a new data/schema field if a RED test proves current data cannot represent the required behavior.

Required behavior/output:

### Priest / FV-PRIEST-01
- deterministic `lowest_health_ally` helper outside enemy selector
- `role_heal`: source, target, raw_heal, effective_heal, overheal
- `role_buff_start` / `role_buff_end`
- measurable `EFFECTIVE_HEALING_HP`, `OVERHEAL_WASTE`, `SUPPORTED_TARGET_SECONDS`, `BUFF_UPTIME`

### Mage / FV-MAGE-01
- consume existing `cluster` priority deterministically
- primary + bounded same-lane collateral AoE
- magic damage channel uses magic resistance
- `role_aoe_hit`
- measurable primary damage, collateral damage, targets hit
- keep `CONTROL_TARGET_SECONDS = BLOCKED_RUNTIME_OUTPUT` until actual control exists; no fake zero

### Flier / FV-FLIER-01
- use air role + backline priority
- do not clone Assassin bypass state as the implementation
- own deterministic same-lane backline pressure route
- `role_backline_contact` and `role_dive`
- measurable time-to-contact / bypass / dive / pressure
- `AIR_TARGETABILITY_EXPOSURE` remains blocked until real anti-air contract supports it

### Giant / FV-GIANT-01
- preserve existing siege objective path and structure tags
- bounded same-lane slam AoE; exclude air targets
- `role_slam` with affected ids and damage by target
- preserve existing `gate_damage` / `base_damage`

PoC effect amounts/cooldowns in the authority are provisional implementation inputs only. Do not promote them to final product numerics and do not select a final weighted functional-value score/vector.
