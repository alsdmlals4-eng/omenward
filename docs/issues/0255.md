# Issue #255: Phase 2: global building roster and occupation-slot migration

## Issue body
## Goal
Implement the user-confirmed Phase 2 replacement for battlefield construction nodes: one player-only global building roster with capacity `6 + stable Lumern-held forward bases + stable Lumern-held clash zones`.

## Product contract
- Battlefield shows terrain, units, ownership feedback, combat effects, and **one fixed tower per forward base** only.
- Construction pads, per-outpost production buildings, and map-placement interactions are removed from the player path.
- Roster cards are ordered top-to-bottom. Capacity loss locks cards below capacity without deleting their tier/history, refunds, passive effects, or roulette TokenSources; recovery reactivates them top-down.
- Stable forward-base ownership transfers its local fixed tower and contributes a single auditable gold benefit. Capture, stabilizing, neutralizing, and contested states disable that tower and contribute no capacity.
- Stable clash zones contribute capacity but no tower.
- Stage 1 permits read-only roster visibility only; direct roster mutation begins after the tutorial boundary.
- Exact gold values and future building upgrade numerics remain simulation-pending.

## Acceptance criteria
- [ ] RED-first headless contract tests cover capacity, lock/reactivation, passive/token removal, fixed-tower state, no solo tower capture, gold non-duplication, no map-building consumer, and Stage 1 gating.
- [ ] Existing per-outpost node state is migrated to a global roster service without duplicate state authority.
- [ ] Run Command PREPARE renders the roster as the only building interaction surface; roulette remains a separate lower-deck surface.
- [ ] Battlefield contains no construction-pad drawing and renders exactly one fixed tower per forward base.
- [ ] Existing deterministic run-command and battle contracts stay green after targeted regressions are reconciled.
- [ ] Generated visual candidates remain planning-only until provenance and runtime-asset promotion gates are independently satisfied.
- [ ] Runtime and human UX evidence retain explicit NOT_RUN/PARTIAL boundaries.
